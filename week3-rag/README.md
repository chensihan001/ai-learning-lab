# week3-rag：130 行的最小可用 RAG

不调 LangChain、不装向量库，从零把「读文档 → 切块 → 建索引 → 检索 → 拼 prompt → 模型回答」这条链自己写一遍。
目的是能对着面试官讲清楚每一步的取舍，而不是只会 `from langchain import ...`。

## 它现在能做什么

- 读 `corpus/` 下的 `.md` / `.txt`，切成带重叠的块
- 用 **BM25**（纯 Python + 中文二元组分词）检索 top-k 相关块，不花钱、不联网
- 把检索结果拼成带 `[1] [2]` 编号的 prompt，让模型**只依据资料回答并给出引用**
- 三种运行模式：真实模型 / `--no-llm` 只看检索 / `--mock` 验证流程

## 快速开始

```bash
cd week3-rag
pip install -r requirements.txt
cp ../.env.example ../.env      # 填 OPENAI_API_KEY / OPENAI_BASE_URL / MODEL

python test_rag.py                              # 9 个测试，不花钱
python rag.py -q "RAG 为什么要切块" --no-llm      # 只看检索结果
python rag.py -q "BM25 有什么缺点？应该怎么弥补"   # 完整 RAG
python rag.py                                    # 交互模式
```

## 文件说明

| 文件 | 作用 |
|---|---|
| `chunker.py` | 切块：按长度切、在句末标点对齐、相邻块重叠 `overlap` 字 |
| `bm25.py` | 分词（英文整词 + 中文 bigram）与 BM25 打分，带 `explain()` 可查每个词的贡献 |
| `rag.py` | 主流程：建索引 → 检索 → 拼带编号的 prompt → 流式回答 |
| `test_rag.py` | 9 个测试：切块不丢字/不超长/有重叠、排序正确、prompt 带编号、跨文件命中 |
| `corpus/` | 示例语料（换成你自己的笔记/文档才能体现价值） |

## 实测记录（本机，2026-11-23）

两篇示例笔记（约 5000 字）切成 **5 块**，问 "BM25 有什么缺点？应该怎么弥补"：

```
BM25 的缺点：它做不到同义词和换一种说法的语义匹配，比如「怎么加速」匹配不到「性能优化」[2]。

弥补方式：生产系统通常把 BM25 和向量检索混用——BM25 保精确匹配（型号、报错码、
API 名字），向量保语义召回，最后用 RRF 之类的算法把两路结果融合 [1][2]。
```

两个能直接讲的观察：

1. **引用编号不是装饰**。没有编号，你无法判断它是照资料答的还是编的；加了编号，答错时能立刻定位是「检索捞错」还是「模型读错」。
2. **BM25 会把「沾边」的块排进来**。问"为什么切块"，`agent-notes.md` 里讲记忆那一段因为出现"RAG"也被召回（相关度 1.01）。这正是词面检索的短板，也是下一步要加向量检索的理由。

## 三个必须能答的问题

<details>
<summary>1. 为什么第一版用 BM25，而不是直接上向量检索？</summary>

因为要先把「检索」和「生成」两件事分开调。BM25 零依赖、零成本、结果可解释，出错时能定位到具体是哪个词没命中；向量检索多一层 embedding API，跑不通时分不清是维度、归一化、相似度还是模型的问题。工程上先跑通最简链路，再换更强的组件。
</details>

<details>
<summary>2. 块大小怎么定？太大太小各有什么问题？</summary>

块太小：语义被切碎，检索到半句话，模型读不懂；块太大：一块混多个主题，检索召回"沾边噪声"，还白烧 token（上下文越长越贵，且注意力是平方复杂度）。经验值 300–500 字，重叠 50–100 字，并且**要在评测集上试**——参数没有通用最优解，只有针对你的语料和问题分布的最优解。
</details>

<details>
<summary>3. 为什么要先 `--no-llm` 再看模型回答？</summary>

RAG 答错有两类原因：检索没捞到（召回问题）、捞到了但模型读错（生成问题）。`--no-llm` 直接打印检索到的块，能先确认第一类。跳过这步直接看回答，你会把检索错误误判成"模型不听话"，然后去改 prompt——南辕北辙。
</details>
